## 架構理解

> 這一節幫你快速看懂 17 張表怎麼串起來、關鍵設計在做什麼。看完再往下讀個別表定義會更有方向。

### 一、表關聯總圖

**課程四層**（賣什麼 → 買到什麼 → 何時上）——這是本系統最核心的一條線：

```
courses（課種：瑜珈/私教/TRX）
   │
   ├──→ products（方案：「瑜珈10堂$8000」）──→ order_items（買了這個方案）
   │                                              │
   │                                              ↓
   └──← member_packages（權益：張三剩7堂，快照 course_id）
                    │
                    ↓
              reservations（預約：張三約了某場次）──→ trainer_schedules（場次：王教練8/20那堂）
                    │
                    ↓
              session_deduction_logs（銷課紀錄：堂數異動日誌）
```

**訂單鏈**（購物到開課）：

```
users ──→ orders ──→ order_items ──→ member_packages（付款成功才開）
                          │
              products ───┘（買的是哪個商品/方案）
```

**其他關聯**：

| 關係 | 串法 |
|---|---|
| 教練檔案 | `users` ←1:1→ `trainer_details` |
| 場次歸屬 | `trainer_schedules` → `users`(教練) + `courses`(課種) + `rooms`(教室) |
| 購物車 | `users` → `cart_items` → `products` |
| 庫存 | `products` → `inventory_logs` |
| 評論 | `order_items` ←1:1→ `comments`（買過才能評） |
| 聊天 | `users` → `chat_messages`（`room_id` 是房間鍵，**與 `rooms` 教室表無關**） |
| AI 健管 | `users` → `inbody_records` → `ai_health_plans` |

### 二、關鍵設計白話

**① 預留制三計數器**（`member_packages` 的 `reserved` / `used` / `remaining`）
- 一句話：課程包的堂數拆成「已訂未上、已消耗、還能訂」三個數字，恆等式 `total = reserved + used + remaining`。
- 為什麼：訂課當下就先扣（`reserved+1`），所以就算教練漏記核銷，學員的錢也不會錯。這是解決「銷課爭議」的核心。
- 事件：訂課 `reserved+1`、核銷 `reserved−1 used+1`、準時取消 `reserved−1`、遲取消/缺席 `reserved−1 used+1`、到期沒收 `used+N`。

**② 房間鍵**（`chat_messages.room_id`）
- 一句話：兩人聊天的房間 ID，規則是 `min(uid)_max(uid)`，例如會員 12 和教練 47 → `"12_47"`。
- 為什麼：不論誰發訊都落同一個房間，一次查詢就撈到完整對話。
- ⚠️ 陷阱：這個 `room_id` 是**字串房間鍵**，跟 `rooms`（實體教室）表**完全無關**，別接成外鍵。

**③ 單表繼承**（`products` 用 `type` 區分 COURSE / GOODS）
- 一句話：課程方案和實體商品放**同一張表**，用 `type` 欄位區分。
- 為什麼：兩者共用購物車、訂單、金流流程，拆兩張表會讓 `order_items` 難以指向。
- 保障：`CK_products_shape` 這條約束強制型別完整——COURSE 必須有堂數/效期、GOODS 必須沒有，寫錯直接被 DB 擋下。

**④ append-only 日誌**（`session_deduction_logs`）
- 一句話：銷課紀錄只能新增、不能修改刪除，每筆用 `CK_deduct_math`（`after = before + delta`）自我驗證。
- 為什麼：作為退費糾紛的不可竄改依據。要補償就新增一筆 `ADJUST`，絕不改舊紀錄。

**⑤ 冗餘計數器 + 對帳**（`booked_count`、`reserved/used`、`stock`）
- 一句話：這些數字本可由明細算出，但為了併發下的原子扣減而冗餘儲存。
- 守門：四條對帳查詢定期跑，冗餘值必須等於明細算出的值，對不上就是有 bug。

### 三、狀態流轉（status 何時改變）

> 每個 `status` 欄位的值是什麼意思、什麼事件讓它從一個狀態變到另一個。這是組員最容易漏看、但寫程式一定要懂的部分。

#### `reservations`（預約）— 核心狀態機

```
                    ┌──────────────────────────────┐
    訂課            │                              ↓
  ────────→  PENDING ──教練輸入金鑰核銷──→  COMPLETED
             │  │  │
             │  │  └──學員/教練/管理員取消──→  CANCELLED
             │  │
             │  └──排程判定未到場──→  NO_SHOW
             │
             └──（CHECKED_IN：schema 保留，目前實作跳過，直接 PENDING→COMPLETED）
```

| 狀態 | 意思 | 由什麼事件進入 |
|---|---|---|
| `PENDING` | 已預約，待上課 | **訂課**成立（預設值） |
| `COMPLETED` | 已核銷，完成履約 | 教練輸入 8 碼金鑰**核銷** |
| `CANCELLED` | 已取消 | 學員／教練／管理員**取消**（同時填 cancel_type/cancelled_by/cancelled_at） |
| `NO_SHOW` | 未到場 | 排程判定（遲取消未到／缺席） |
| `CHECKED_IN` | （保留）已報到未完成 | ⚠️ schema 定義了但**目前實作未使用**，核銷直接 PENDING→COMPLETED |

**搭配的堂數變動**（預留制）：訂課 `reserved+1`、核銷 `reserved−1 used+1`、準時取消 `reserved−1`、遲取消/NO_SHOW `reserved−1 used+1`。

#### `member_packages`（課程權益）

```
   付款開通          到期排程
  ─────────→ ACTIVE ─────────→ EXPIRED
               │
               └──退費──→ REFUNDED
```

| 狀態 | 意思 | 由什麼事件進入 |
|---|---|---|
| `ACTIVE` | 生效中，可約課 | 綠界**付款成功**開通（預設值） |
| `EXPIRED` | 已到期 | 排程檢查 `expire_date < 今天`，到期沒收剩餘堂數（寫 EXPIRE log） |
| `REFUNDED` | 已退費 | 退費流程（保留，骨架未實作） |

#### `orders`（訂單）

```
  結帳         綠界付款成功                出貨(實體商品)      收貨
 ─────→ UNPAID ──────────→ PAID ──────────→ SHIPPED ──────→ COMPLETED
          │                                                    ↑
          ├──付款失敗──→ FAILED                                │
          │                              純課程訂單付款後直達 ──┘
          └──取消──→ CANCELLED
```

| 狀態 | 意思 | 由什麼事件進入 |
|---|---|---|
| `UNPAID` | 待付款 | 建立訂單（預設值） |
| `PAID` | 已付款 | 綠界回調**付款成功** |
| `SHIPPED` | 已出貨 | 實體商品出貨（純課程訂單跳過） |
| `COMPLETED` | 已完成 | 收貨完成／純課程付款後完成 |
| `CANCELLED` | 已取消 | 付款前取消 |
| `FAILED` | 付款失敗 | 綠界回報失敗 |

#### `coupons`（優惠券）

| 狀態 | 意思 | 由什麼事件進入 |
|---|---|---|
| `ACTIVE` | 生效中，可兌換 | 後台建立（預設值）|
| `INACTIVE` | 停用 | 後台手動停用 |

（券的「用完」不是靠 status，而是 `used_count >= total_quantity`；「過期」看 `end_at`。status 只管人為啟用/停用。）

#### `users`（帳號）

| 狀態 | 意思 | 由什麼事件進入 |
|---|---|---|
| `ACTIVE` | 正常 | 註冊（預設值） |
| `SUSPENDED` | 停權 | 管理員停權（SYSTEM 系統帳號也是此狀態） |

#### 簡單開關（無流轉，只是啟用/停用）

`courses` / `rooms` / `products` 的 `status` 只有 `ACTIVE`（上架/啟用）與 `INACTIVE`（下架/停用），由管理員手動切換，無狀態機。

### 四、資料流走查

三個核心流程各碰哪些表（照實際執行順序）：

**訂課**（悲觀鎖，鎖順序 S→P→R）
```
1. 鎖 trainer_schedules（S）── 檢查名額、booked_count+1
2. 鎖 member_packages（P）─── 檢查堂數、reserved+1
3. 寫 reservations（R）────── 產生 8 碼核銷金鑰
4. 寫 session_deduction_logs ─ 記一筆 DEDUCT
```

**買課**（綠界付款成功後開權益）
```
1. 寫 orders ──────────── 訂單主檔（含綠界交易編號）
2. 寫 order_items ─────── 訂單明細（快照價格/名稱）
3. 寫 member_packages ─── 開課程包（UQ order_item_id 防重複開）
   （products 提供方案內容，扣 stock 用樂觀鎖）
```

**核銷**（教練輸入學員的 8 碼，鎖順序 S→R→P）
```
1. 查 reservations ─────── 用金鑰找 PENDING 的預約
2. 鎖 trainer_schedules ── 確認場次、驗證是本場教練（不改 S 但要鎖）
3. 改 reservations ─────── status → COMPLETED
4. 鎖 member_packages ──── reserved−1, used+1（可用堂數不變，不寫 log）
```

## 1. `users` — 使用者

會員、教練、管理員共用的帳號主檔，同時支援密碼登入與 Google OAuth。

| 欄位 | 型別 | 鍵 | NULL | 預設 | 說明 |
|---|---|---|---|---|---|
| `id` | bigint IDENTITY(1,1) | PK | N | | |
| `first_name` | nvarchar(50) | | N | | 名 |
| `last_name` | nvarchar(50) | | N | | 姓 |
| `dob` | date | | Y | | 生日；AI 健管推算年齡 |
| `email` | varchar(100) | UK | N | | 登入帳號 |
| `phone` | varchar(20) | | Y | | 聯絡電話 |
| `gender` | varchar(10) | | Y | | 性別；AI 健管計算 BMR |
| `role` | varchar(20) | | N | | 角色 |
| `pwd_hash` | varchar(255) | | Y | | BCrypt 雜湊；OAuth 使用者無密碼 |
| `oauth_provider` | varchar(20) | UK* | Y | | OAuth 供應商（`GOOGLE`） |
| `oauth_sub` | varchar(255) | UK* | Y | | OAuth 穩定使用者 ID |
| `status` | varchar(20) | | N | `'ACTIVE'` | 帳號狀態 |
| `created_at` | datetime2 | | N | `@NOW` | |
| `updated_at` | datetime2 | | N | `@NOW` | |

- `role`：`MEMBER`／`TRAINER`／`ADMIN`
- `gender`：`M`／`F`／`OTHER`
- `status`：`ACTIVE`／`SUSPENDED`
- 每個帳號至少須有一種登入方式（密碼或 OAuth）；`oauth_provider` 與 `oauth_sub` 兩欄同時有值或同時為空。

**約束與唯一索引**

```sql
CONSTRAINT CK_users_role            CHECK (role   IN ('MEMBER','TRAINER','ADMIN')),
CONSTRAINT CK_users_status          CHECK (status IN ('ACTIVE','SUSPENDED')),
CONSTRAINT CK_users_gender          CHECK (gender IN ('M','F','OTHER')),
CONSTRAINT CK_users_oauth_provider  CHECK (oauth_provider IN ('GOOGLE')),
CONSTRAINT CK_users_auth            CHECK (pwd_hash IS NOT NULL OR oauth_sub IS NOT NULL),
CONSTRAINT CK_users_oauth           CHECK (
  (oauth_provider IS NULL     AND oauth_sub IS NULL)
  OR
  (oauth_provider IS NOT NULL AND oauth_sub IS NOT NULL)
)

CREATE UNIQUE INDEX UX_users_email ON users(email);
CREATE UNIQUE INDEX UX_users_oauth ON users(oauth_provider, oauth_sub)
    WHERE oauth_sub IS NOT NULL;
```

## 5. `trainer_schedules` — 課程場次

教練排定的具體上課時段（含日期、時間、地點、名額）。同一課種可開出多個場次。

| 欄位 | 型別 | 鍵 | NULL | 預設 | 說明 |
|---|---|---|---|---|---|
| `id` | bigint IDENTITY(1,1) | PK | N | | |
| `trainer_id` | bigint | FK | N | | → `users.id`，開課教練 |
| `course_id` | bigint | FK | N | | → `courses.id`，這場開什麼課 |
| `room_id` | bigint | FK | Y | | → `rooms.id`；NULL＝不佔固定教室 |
| `start_at` | datetime2 | UK* | N | | 時段起（含日期） |
| `end_at` | datetime2 | | N | | 時段訖（可跨日） |
| `schedule_date` | AS (`CAST(start_at AS date)`) PERSISTED | IX | | | 歸屬日＝開始日（計算欄位） |
| `capacity` | int | | N | | 名額 |
| `booked_count` | int | | N | `0` | 已占名額 |
| `is_available` | bit | | N | `1` | 教練是否開放此場次 |
| `created_at` | datetime2 | | N | `@NOW` | |

- `end_at > start_at`、`capacity >= 1`、`booked_count` 介於 0 與 `capacity` 之間
- `is_available` 表示「教練是否開放此場次」，與「是否已被訂」（`booked_count`）不同

**約束與唯一索引**

```sql
CONSTRAINT CK_schedule_time     CHECK (end_at > start_at),
CONSTRAINT CK_schedule_capacity CHECK (capacity >= 1),
CONSTRAINT CK_schedule_booked   CHECK (booked_count BETWEEN 0 AND capacity)

CREATE UNIQUE INDEX UX_schedule_slot ON trainer_schedules(trainer_id, start_at);
```

## 6. `reservations` — 預約

學員對某個場次的預約。教練、課種、教室、時段皆透過 `schedule_id` JOIN 取得。

| 欄位 | 型別 | 鍵 | NULL | 預設 | 說明 |
|---|---|---|---|---|---|
| `id` | bigint IDENTITY(1,1) | PK | N | | |
| `schedule_id` | bigint | FK, UK* | N | | → `trainer_schedules.id` |

- `discount_type`：`FIXED`／`PERCENT`；`status`：`ACTIVE`／`INACTIVE`
- `discount_value > 0`；PERCENT 的值須介於 0 與 1；`end_at > start_at`
- **超發兜底**：`used_count` 不可超過 `total_quantity`（無限量則跳過）

**約束與唯一索引**

```sql
CONSTRAINT CK_coupons_type     CHECK (discount_type IN ('FIXED','PERCENT')),
CONSTRAINT CK_coupons_status   CHECK (status IN ('ACTIVE','INACTIVE')),
CONSTRAINT CK_coupons_value    CHECK (discount_value > 0),
CONSTRAINT CK_coupons_minspend CHECK (min_spend >= 0),
CONSTRAINT CK_coupons_shape    CHECK (
    (discount_type = 'PERCENT' AND discount_value > 0 AND discount_value < 1)
    OR (discount_type = 'FIXED' AND max_discount IS NULL)
),
CONSTRAINT CK_coupons_time     CHECK (end_at > start_at),
CONSTRAINT CK_coupons_quantity CHECK (total_quantity IS NULL OR total_quantity >= 0),
CONSTRAINT CK_coupons_used     CHECK (total_quantity IS NULL OR used_count <= total_quantity)

CREATE UNIQUE INDEX UX_coupons_code ON coupons(code);
```

## 19. `coupon_usages` — 優惠券使用紀錄

一張券多人用 → `coupons` 一對多 `coupon_usages`。`discount_amount` 快照實際折抵（券日後改規則不影響歷史）。

| 欄位 | 型別 | 鍵 | NULL | 預設 | 說明 |
|---|---|---|---|---|---|
| `id` | bigint IDENTITY(1,1) | PK | N | | |
| `coupon_id` | bigint | FK | N | | → `coupons.id`，用了哪張券 |
| `user_id` | bigint | FK | N | | → `users.id`，誰用的 |
| `order_id` | bigint | FK, UK | N | | → `orders.id`，用在哪張訂單 |
| `discount_amount` | decimal(10,2) | | N | | 實際折抵金額（快照）|
| `created_at` | datetime2 | | N | `@NOW` | |

- `discount_amount >= 0`
- **冪等**：同一張訂單只能用一次券（`UQ(order_id)`，防重複折抵）

**約束與唯一索引**

```sql
CONSTRAINT CK_couponusage_amount CHECK (discount_amount >= 0),
CONSTRAINT UQ_couponusage_order  UNIQUE (order_id)
```
